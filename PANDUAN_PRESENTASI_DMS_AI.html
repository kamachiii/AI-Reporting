1. Ringkasan Cepat: Bicara Apa di 30 Detik Pertama?

"Selamat pagi/siang Bapak/Ibu penguji. Platform yang saya bangun ini adalah DMS AI Platform, yaitu asisten cerdas untuk dealer mobil dan motor. Karyawan dealer sering kesulitan membuat laporan cepat karena database dealer sangat rumit (bisa mencapai 2.300+ tabel) dengan istilah akuntansi yang kompleks (seperti hpdpp dan hpunit).

Melalui platform ini, karyawan cukup bertanya dalam bahasa Indonesia sehari-hari di chat, dan sistem akan menghasilkan data nyata dari database dealer secara instan, terverifikasi keamanannya, dan tanpa halusinasi data."

2. Tiga Masalah Nyata di Lapangan & Solusi Kita

Tantangan / Masalah Industri

  • Database Raksasa: Satu dealer memiliki lebih dari 2.380 tabel tanpa relasi foreign key fisik.
  • Text-to-SQL Naif Rusak: AI biasa sering salah sintaks, halusinasi nama tabel, dan query berat bikin server macet.
  • Privasi Data: Data nasabah dan angka finansial dilarang keluar ke server pihak ketiga.

Solusi di Platform Ini

  • Two-Tier Engine: 90% query memakai rencana JSON terstruktur (Tier 1). Query rumit dijaga Verifier 6 Gerbang (Tier 2).
  • Knowledge Base SSOT: Kamus istilah terpusat (2.400+ aturan) & Virtual Foreign Key.
  • On-Premises Isolation: Data mentah dieksekusi lokal di server cabang (data trust model).

4. Jawaban Tangkas untuk Pertanyaan Pembunuh Penguji (Q&A Defense)

Q1: "Bagaimana kamu menjamin AI tidak merusak database (seperti DROP / DELETE / UPDATE)?"

Jawaban:
"Sistem kami menerapkan Verifier 6 Gerbang yang bersifat default-deny. Sebelum query dieksekusi, sistem memeriksa bahwa perintah wajib SELECT tunggal, memvalidasi pohon sintaks (AST) dengan sqlglot, membatasi kompleksitas (maks 5 join, budget limit), dan saat dieksekusi di database cabang, kami mengunci transaksinya secara fisik dengan SET TRANSACTION READ ONLY serta membatasi waktu maksimal 10 detik."

Q2: "Apakah data pelanggan atau angka transaksi dealer dikirim ke OpenAI / Anthropic?"

Jawaban:
"Sama sekali tidak. Kami menerapkan On-Premises Data Trust Model. Yang dikirim ke model AI hanyalah nama-nama kolom dan kamus istilah (Knowledge Base) untuk merancang logika query. Hasil data riil pelanggan dan uang dieksekusi dan diproses 100% di server lokal kami."

Q3: "Banyak database lama tidak punya relasi Foreign Key fisik. Bagaimana AI bisa menggabungkan tabel?"

Jawaban:
"Kami mengembangkan fitur Virtual Foreign Key pada modul Knowledge Base. Relasi antar-kolom (misal untt_pembelian.norangka ke untt_datakendaraan.norangka) didaftarkan di tingkat aplikasi, lalu disuntikkan secara dinamis ke skema memori saat runtime tanpa perlu mengubah DDL fisik database klien (Zero DDL Impact)."

Q4: "Bagaimana cara kerja Number Check pada Presenter? Apa gunanya?"

Jawaban:
"LLM sering berhalusinasi saat membuat kalimat ringkasan. Di sistem kami, modul presenter.py mengekstrak seluruh angka dari teks ringkasan AI, lalu memvalidasi secara mekanis apakah angka tersebut benar-benar ada di baris tabel hasil query. Jika AI mengarang angka yang tidak ada, ringkasan dibatalkan dan sistem otomatis memakai template deterministik yang pasti benar."

Q5: "Apa itu tombol Tier 2 di tabel Koneksi? Mengapa ada tombol itu?"

Jawaban:
"Itu adalah Safety Switch per cabang. Secara default, cabang menggunakan Tier 1 (mode JSON deterministik). Tier 2 (SQL bebas) hanya boleh dibuka jika cabang tersebut sudah lulus pengujian Golden-Set Benchmark dengan akurasi $\ge 95\%$ dan 0 pelanggaran keamanan. Di database kita, cabang TST_01 sudah lulus 100% sehingga bisa diaktifkan, sedangkan cabang JKT_01 belum pernah diuji sehingga tombol otomatis menolak aktivasi."

Q6: "Kok bisa kamu membangun sistem sebesar ini? Bagaimana metodologinya?"

Jawaban:
"Saya menggunakan pendekatan Spec-Driven Development dan Test-Driven Development (TDD) dengan bantuan AI Agentic Coding. Saya tidak langsung koding, melainkan merancang arsitektur Two-Tier dan gerbang keamanan terlebih dahulu di dokumen spesifikasi, membuat 507 unit tests untuk katalog serangan SQL, lalu membagi implementasi per fase terverifikasi dengan standar gate CI (0 error linter dan exit code 0)."

5. Peta Kode & Lokasi File (Jika Penguji Minta Buka Kodingan)

Modul / File Lokasi Berkas Fungsi Utama yang Perlu Dijelaskan
Orchestrator Pipeline backend/app/services/chat_pipeline.py Mengatur alur utama: cek rate limit, resolve tenant, replay SQL Memory, eksekusi, presenter, hingga audit log.
Tier 1 Planner backend/app/services/query_planner.py Meminta LLM menyusun rencana JSON terstruktur (bukan SQL) dan normalisasi toleransi filter tanggal/tipe data.
SQL Composer backend/app/services/sql_composer.py Mengubah rencana JSON menjadi SQL berparameter ($1, $2) secara deterministik dan join otomatis.
Tier 2 Generator backend/app/services/tier2_generator.py Router LLM untuk SQL bebas + loop self-repair (maks 2x) dan fallback otomatis ke Tier 1 jika gagal.
Security Verifier backend/app/services/sql_guard.py & query_verifier.py Verifier 6 Gerbang: AST parsing (sqlglot), whitelist fitur versioned, budget complexity, dan EXPLAIN pre-flight.
Confinement Executor backend/app/services/query_executor.py Gerbang #6: Mengeksekusi SQL di DB tenant dalam transaksi READ ONLY, timeout 10 detik, dan limit 500 baris.
Presenter & Guard backend/app/services/presenter.py Membuat ringkasan bahasa Indonesia + validasi mekanis NUMBER CHECK anti-halusinasi angka.
Knowledge Base backend/app/services/knowledge_base.py Menggabungkan Global KB & Tenant KB, membentuk skema efektif, dan menyuntikkan Virtual Foreign Key.
Tenant Isolation backend/app/services/tenant_pool.py Pool koneksi database tenant terisolasi per cabang dengan dekripsi kredensial Fernet.
Eval Harness backend/app/services/eval_runner.py Menjalankan benchmark golden-set dan menegakkan gate aktivasi Tier 2 (≥ 95% pass rate & 0 pelanggaran).
